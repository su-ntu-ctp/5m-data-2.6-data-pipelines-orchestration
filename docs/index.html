🔄 Data Pipelines & Orchestration Guide

Meltano ELT → dbt Transform → Dagster Orchestration

📚 From ETL to ELT

Due to the rise of cloud data warehouses, data pipelines have shifted from Extract, Transform, Load (ETL) to Extract, Load, Transform (ELT). Instead of transforming data before it lands in the warehouse, you load the raw data first and transform it afterwards using the warehouse's own compute power.

In plain English

ETL is like cooking a meal before you put it in the fridge. ELT is like putting the raw groceries straight in the fridge, then cooking straight from there whenever you need a dish. Modern cloud warehouses (BigQuery, Snowflake) are powerful enough to do the "cooking" (transformation) themselves, so we load raw data first and transform it later — that's what makes ELT the preferred pattern today.

In this lesson: Meltano handles ingestion (Extract + Load), dbt handles Transform, and Dagster orchestrates the whole thing on a schedule.

🔑 Key Terms for Beginners

These words come up constantly in this guide. Skim these once and the rest of the page will make a lot more sense.

Extractor (Tap)
A Meltano plugin that reads data from a source — an API, a database — and outputs it in a standard format.
Loader (Target)
A Meltano plugin that receives the data stream from a tap and writes it to a destination, like BigQuery.
Data Warehouse
A database built for analysis rather than day-to-day apps — in this lesson, BigQuery.
dbt Model
A saved SQL SELECT statement that dbt compiles and runs in the warehouse to produce a clean table or view.
Software-Defined Asset
Dagster's unit of a pipeline — a piece of data (a table, a DataFrame, a file) and the function that produces it.
Orchestration
Automatically running pipeline steps in the right order, on a schedule, without a human clicking "run" each time.

Getting Started

Work through the tabs above in order: Meltano ingests data, dbt transforms it, Dagster automates both.

🚀 Create a Meltano Project

In plain English

In unit 2.4 you wrote Python scripts to call the GitHub API by hand. That works once, but production pipelines need to run on a schedule, retry on failure, and scale to many sources without rewriting code each time. Meltano does all of this through configuration instead of custom code.

meltano init meltano-ingestion
cd meltano-ingestion

Creates a new Meltano project folder for the GitHub → BigQuery pipeline.

meltano config set meltano python python3.11

Meltano installs each tap and target into its own virtual environment. This ensures they all use Python 3.11, matching your conda environment.

⚠️ Each data source gets its own Meltano project. A second project for Postgres (meltano-resale) must be created in the repo root — never inside meltano-ingestion.

📥 Extractors (Taps)

A tap is a plugin that reads data from a source and outputs it in a standardised format, so you don't have to write API clients from scratch.

meltano add tap-github
meltano config set tap-github --interactive

Set auth_token (your GitHub personal access token) and repositories: ["pandas-dev/pandas"]

meltano config test tap-github
meltano select tap-github --list --all

Select only the fields you need — extracting everything wastes transfer time, storage, and adds noise.

meltano select tap-github releases tag_name
meltano select tap-github releases body
meltano select tap-github releases published_at
meltano init meltano-resale
cd meltano-resale
meltano config set meltano python python3.11
meltano add tap-postgres
meltano config set tap-postgres --interactive

Configure database: postgres, filter_schemas: ['public'], host, password, port: 5432, user.

💡 filter_schemas: ['public'] stops the tap from introspecting system schemas it doesn't need.
meltano config test tap-postgres
meltano select tap-postgres "public-resale_flat_prices_from_jan_2017" "*"

The first argument selects the table (stream), the second ("*") selects all its columns — both are required.

🧪 Test Locally with target-jsonl

💡 Before sending data to BigQuery, dump it to a local JSON file first to confirm the extractor works.
meltano add target-jsonl
meltano run tap-github target-jsonl

The extracted data lands in the output/ directory. Open it and check for tag_name, body, and published_at.

📤 Loaders (Targets): target-bigquery

A target receives the standardised data stream from a tap and writes it to a destination — handling table creation, schema inference, and batching automatically.

meltano add target-bigquery
meltano config set target-bigquery --interactive

Key options

credentials_path (service account JSON key), dataset (ingestion or resale), denormalized: true, flattening_enabled: true, flattening_max_depth: 1, method: batch_job, project.

💡 flattening_enabled turns nested JSON fields into separate columns; denormalized expands repeated fields into rows.

For the resale dataset (~180,000+ rows), also set batch_size: 104857600 (100MB) for fewer, faster round-trips.

⚠️ Known issue (setuptools ≥ 81.0.0): removed pkg_resources, which the target-bigquery plugin needs. Fix: in meltano.yml, under the target-bigquery plugin's pip_url, add setuptools<80 after the git URL.

meltano run tap-github target-bigquery
meltano run tap-postgres target-bigquery

Check BigQuery afterwards — you should see a releases table (from GitHub) and a public_resale_flat_prices_from_jan_2017 table (from Postgres). Note: numeric-looking Postgres columns land as STRING — that's expected, and gets fixed in dbt.

🚀 Create a dbt Project

In plain English

Meltano's job is to get data into the warehouse as faithfully as possible — it doesn't clean it. The raw table still has string-typed numbers exactly as they came from Postgres. dbt is where you apply business logic: casting types, calculating derived columns, and building models that are actually ready for analysis.

cd ..
dbt init resale_flat

Fill in: service account, path to the JSON key file, dataset resale, and your GCP project ID.

⚠️ Create the dbt project from the repo root — not inside meltano-resale.

resale_flat:
  outputs:
    dev:
      dataset: resale
      job_execution_timeout_seconds: 300
      job_retries: 1
      keyfile: /path/to/your-key-file.json
      location: US
      method: service-account
      priority: interactive
      project: your-gcp-project-id
      threads: 1
      type: bigquery
  target: dev

Keeping profiles.yml inside the project (instead of the global ~/.dbt/profiles.yml) makes the project self-contained and portable.

📋 Sources & Models

1. Source — where the raw data lives

A source tells dbt which dataset and table to read, so your SQL can reference it with {{ source(...) }}.

version: 2

sources:
  - name: resale
    schema: resale
    tables:
      - name: public_resale_flat_prices_from_jan_2017

2. prices.sql — clean the raw table

Casts the string-typed numeric columns and adds a calculated price_per_sqm column.

{{ config(materialized='table') }}

with source as (
    select * from {{ source('resale', 'public_resale_flat_prices_from_jan_2017') }}
)

select
    month,
    town,
    flat_type,
    block,
    street_name,
    storey_range,
    cast(floor_area_sqm as numeric) as floor_area_sqm,
    flat_model,
    lease_commence_date,
    remaining_lease,
    cast(resale_price as numeric) as resale_price,
    cast(resale_price as numeric) / cast(floor_area_sqm as numeric) as price_per_sqm
from source

3. prices_by_town_type_model.sql — aggregate for analysis

Averages price metrics by town, flat type, and flat model — useful directly for dashboards.

{{ config(materialized='table') }}

select
    town,
    flat_type,
    flat_model,
    avg(floor_area_sqm) as avg_floor_area_sqm,
    avg(resale_price) as avg_resale_price,
    avg(price_per_sqm) as avg_price_per_sqm
from {{ ref('prices') }}
group by town, flat_type, flat_model
order by town, flat_type, flat_model
💡 {{ ref('prices') }} tells dbt this model depends on prices — dbt runs them in the correct order automatically.

⚙️ Materialization

Before running, remove the generated example block from dbt_project.yml and set the default materialization:

models:
  resale_flat:
    +materialized: table
💡 materialized: table means dbt builds a physical table each run (as opposed to a view, which re-runs the query every time it's read).

🔄 Running dbt

1

Check the connection

cd resale_flat
dbt debug

A "Profile should not be None" error usually means you're not inside the resale_flat folder.

2

Run the models

dbt run

Builds prices and prices_by_town_type_model as new tables in the resale dataset.

Verify in BigQuery: preview prices — floor_area_sqm/resale_price should now be numeric, with a price_per_sqm column. Preview prices_by_town_type_model — grouped and sorted by town, flat type, flat model.

⚙️ Why Orchestration?

You can run Meltano and dbt manually from the command line — but production pipelines need to run automatically, with scheduling, dependency management, monitoring, and alerting.

In plain English

Dagster is what clicks "run" for you — every night at midnight, in the right order, and it tells you the moment something breaks instead of you finding out days later.

Tool Model Strengths
Dagster Asset-centric Strong lineage, great UI, Python-native
Airflow Task-centric (DAG) Very mature, large ecosystem
Prefect Flow-centric Simple to start, cloud-managed option

🚀 Create a Dagster Project

conda activate dagster
dagster project scaffold --name dagster-orchestration
cd dagster-orchestration

Generates dagster_orchestration/assets.py (your data assets) and dagster_orchestration/definitions.py (wires assets, jobs, and schedules together).

⚠️ Create this from the repo root — not inside resale_flat. Also add a .env file with GITHUB_TOKEN='<your-token>'.

🧩 Software-Defined Assets

An asset is a logical unit of data — a table, a file, a DataFrame — produced by a function. This project defines two:

  • pandas_releases — calls the GitHub API and returns a DataFrame of pandas releases
  • summary_statistics — depends on pandas_releases, and counts mentions of "feature", "bug", "performance" in each release's summary
💡 Because summary_statistics declares pandas_releases: pd.DataFrame as a parameter, Dagster infers the dependency automatically and runs pandas_releases first.
import base64
import dotenv
import os
from io import BytesIO

import matplotlib.pyplot as plt
import pandas as pd
import requests
from dagster import AssetExecutionContext, MetadataValue, asset

dotenv.load_dotenv()

@asset
def pandas_releases(
    context: AssetExecutionContext,
) -> pd.DataFrame:
    access_token = os.getenv("GITHUB_TOKEN")
    response = requests.get(
        "https://api.github.com/repos/pandas-dev/pandas/releases?per_page=100",
        headers={
            "Accept": "application/vnd.github+json",
            "Authorization": f"Bearer {access_token}",
        },
        timeout=30,
    )

    releases_with_essential_fields = [
        {
            "version": release["tag_name"],
            "published_at": release["published_at"],
            "summary": release["body"],
        }
        for release in response.json()
    ]
    df = pd.DataFrame(releases_with_essential_fields)
    df["published_at"] = pd.to_datetime(df["published_at"])

    context.add_output_metadata(
        metadata={
            "num_records": len(df),
            "preview": MetadataValue.md(
                df.sort_values("published_at", ascending=False).head().to_markdown()
            ),
        }
    )

    return df


@asset
def summary_statistics(
    context: AssetExecutionContext,
    pandas_releases: pd.DataFrame,
) -> pd.DataFrame:
    counts = {
        "new_features": pandas_releases.summary.str.contains("feature").sum(),
        "bug_fixes": pandas_releases.summary.str.contains("bug").sum(),
        "performance_improvements": pandas_releases.summary.str.contains(
            "performance"
        ).sum(),
    }

    plt.figure(figsize=(10, 6))
    plt.bar(list(counts.keys()), list(counts.values()))
    plt.xticks(rotation=45, ha="right")
    plt.title("Count of Releases by Type in Pandas")
    plt.tight_layout()

    buffer = BytesIO()
    plt.savefig(buffer, format="png")
    image_data = base64.b64encode(buffer.getvalue())

    md_content = f"![img](data:image/png;base64,{image_data.decode()})"
    context.add_output_metadata(metadata={"plot": MetadataValue.md(md_content)})

    return pd.DataFrame(
        {"type": counts.keys(), "count": counts.values()}
    )

Both assets also attach metadata (a data preview, a bar chart) that shows up directly in the Dagster UI.

⏰ Jobs & Schedules

A job targets a selection of assets to materialize together. A schedule starts a run of a job at a specified time.

from dagster import (
    AssetSelection,
    Definitions,
    ScheduleDefinition,
    define_asset_job,
    load_assets_from_modules,
)

from . import assets

all_assets = load_assets_from_modules([assets])

pandas_job = define_asset_job(name="pandas_job", selection=AssetSelection.all())

pandas_schedule = ScheduleDefinition(
    name="pandas_schedule",
    job=pandas_job,
    cron_schedule="0 0 * * *"  # every day at midnight
)

defs = Definitions(
    assets=all_assets,
    jobs=[pandas_job],
    schedules=[pandas_schedule],
)
💡 cron_schedule="0 0 * * *" means "at 00:00 every day." crontab.guru is handy for reading cron syntax.

🖥️ Run the Pipeline

1

Launch the Dagster UI

dagster dev

Open http://localhost:3000

2

Materialize the assets

Navigate to Jobs → pandas_job, then click "Materialize all" to trigger a run manually.

3

Check the run & schedule

The Runs tab shows live logs for each run. The Automation tab on pandas_job shows the daily midnight schedule.

✨ Best Practices

📁

One Project per Source

Give each data source its own Meltano project — don't mix GitHub and Postgres config in one folder

🔐

Secrets Stay Out of Git

Non-sensitive config goes in meltano.yml; tokens and keys go in .env, never committed

🎯

Select Only What You Need

Extract specific entities and attributes instead of everything — less cost, less noise

🧱

Let dbt Own Transformation

Keep Meltano's job to faithful loading; do type casting and business logic in dbt models

🔗

Model Dependencies Explicitly

Use {{ ref(...) }} in dbt and function parameters in Dagster assets so tools resolve run order for you

📊

Monitor in One Place

Use the Dagster UI to see run history, logs, and asset metadata instead of scattered terminal output

🎓 Key Takeaways

  • ELT (not ETL) is the modern pattern because cloud warehouses can transform data efficiently after loading
  • Meltano uses taps (extractors) and targets (loaders) to move data with configuration, not custom code
  • dbt transforms raw warehouse tables into clean, analytics-ready models using plain SQL
  • Dagster orchestrates pipelines around software-defined assets — what data exists, not just what tasks run
  • Jobs and schedules turn a manual, one-off pipeline into an automated, monitored system
