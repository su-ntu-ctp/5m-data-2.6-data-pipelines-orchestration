🔍 Data Testing Guide

Master data quality with Great Expectations & DBT Testing

📚 What is Data Testing?

Data testing is an important part of data quality management. It verifies that data satisfies expected properties.

In plain English

Imagine a food inspector checking a delivery of ingredients before a restaurant uses them: are the eggs actually eggs, are there the right number of boxes, is nothing expired? Data testing does the same job for data — it checks that the numbers, dates, and categories in your dataset look the way they're supposed to before you build reports or models on top of them.

If bad data gets in and nobody checks it, every dashboard and analysis built on it will quietly be wrong too. Testing catches that early.

Also known as: Data validation, data quality assurance, data quality control, data quality assessment

🔑 Key Terms for Beginners

A handful of words come up constantly in this guide. Skim these once and the rest of the page will make a lot more sense.

Pipeline
The series of steps data moves through: extracted from a source, transformed, then loaded somewhere useful.
Schema
The "shape" of a dataset — which columns exist, and what type of value (text, number, date) each one should hold.
Data Warehouse
A database built for analysis rather than day-to-day apps — e.g. BigQuery, Snowflake, Redshift.
Validation
The act of checking that data meets a rule, e.g. "this column should never be empty."
Model (in DBT)
A saved SQL query that transforms raw data into a clean, reusable table or view.
Orchestration
Automatically running your pipeline steps in the right order, on a schedule, without a human clicking "run" each time.

🚀 Installation & Setup

In plain English

Great Expectations is a Python library that lets you write down rules about your data ("this column must be numbers between 0 and 100") and then automatically checks a real dataset against those rules. 📋 Core Concepts

In plain English

Think of these four concepts as a filing system: the Data Context is the filing cabinet itself, a Data Source is which drawer your files are in (a folder, a cloud bucket, a database), a Data Asset is a labelled folder of related files, and a Batch is the actual stack of paper you pull out to inspect right now.

1. Data Context

Defines storage location for metadata, configurations, and validation results

💡 All GX scripts start with creating a Data Context
context = gx.get_context()

2. Data Sources

Tell GX where your data is located and how to connect to it

Amazon S3 Azure Blob Google Cloud Local Files 
source_folder = "data/"
data_source_name = "resale_flat"

data_source = context.data_sources.add_pandas_filesystem(
    name=data_source_name, 
    base_directory=source_folder
)

3. Data Assets

A collection of related records within a Data Source

asset_name = "resale_csv_files"
file_csv_asset = data_source.add_csv_asset(name=asset_name)

4. Batch Definition

Request all records or a subset from a Data Asset

batch_definition = file_data_asset.add_batch_definition_path(
    name="resale_flat_201701_202306.csv",
    path="resale_flat_201701_202306.csv"
)

batch = batch_definition.get_batch()

✅ Creating Expectations

Single Expectation

preset_expectation = gx.expectations.ExpectColumnMaxToBeBetween(
    column="lease_commence_date",
    min_value=1,
    max_value=2020
)

validation_results = batch.validate(preset_expectation)

Expectation Suite

💡 Group multiple expectations together for comprehensive validation
suite_name = "sctp_expectation_suite"
suite = gx.ExpectationSuite(name=suite_name)
suite = context.suites.add(suite)
suite.add_expectation(preset_expectation)

Validation Definition

definition_name = "sctp_validation_definition"
validation_definition = gx.ValidationDefinition(
    data=batch_definition,
    suite=suite,
    name=definition_name
)

validation_results = validation_definition.run()

🚀 DBT Testing Setup

DBT provides built-in tests and can be extended with powerful testing packages

In plain English

If Great Expectations checks data on the way in, DBT tests check data on the way out — after you've transformed raw data into clean tables. A DBT test is really just a small SQL question, like "does any row break this rule?" — if the answer is "yes, some rows do," the test fails and tells you exactly which model to look at.

📦 Installing dbt_utils

packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0

Create this file in your DBT project root directory

dbt deps

This will download and install the dbt_utils package

✅ dbt_utils Tests

accepted_range Test

Check if values are within an acceptable range

- name: date
  tests:
    - dbt_utils.accepted_range:
        min_value: "PARSE_DATE('%F', '2012-01-01')"
        max_value: "CURRENT_DATE()"
💡 Great for validating date ranges or numeric boundaries

expression_is_true Test

Validate complex business logic across multiple columns

tests:
  - dbt_utils.expression_is_true:
      expression: "ROUND(sale_dollars, 1) = TRUNC(bottles_sold * state_bottle_retail, 1)"
💡 This is a model-level test - place it outside the columns section

📦 Installing dbt-expectations

packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0
  - package: metaplane/dbt_expectations
    version: 0.10.9

Add dbt-expectations to your packages file

✅ dbt-expectations Tests

Column Type Validation

Ensure columns have the correct data types

- name: invoice_and_item_number
  tests:
    - dbt_expectations.expect_column_values_to_be_of_type:
        column_type: string

- name: date
  tests:
    - dbt_expectations.expect_column_values_to_be_of_type:
        column_type: date
💡 Add type tests for all critical columns to catch schema changes early

⚙️ Orchestration with Dagster

Automate and schedule your data testing workflows with orchestration tools

🚀 Why Orchestration?

Orchestration allows you to automate your data pipelines, schedule testing workflows, manage dependencies, and monitor data quality continuously in production environments.

In plain English

So far you've run commands by hand. Orchestration is what happens when a tool like Dagster clicks "run" for you — every night at 2am, in the right order (ingest, then validate, then transform, then test), and it tells you the moment something breaks instead of you finding out days later.

📦 Dagster for Data Testing

💡 Dagster provides powerful capabilities for orchestrating both Meltano and DBT pipelines with built-in testing support

Sample Dagster Configuration

from dagster import Definitions, ScheduleDefinition, job
from dagster_meltano import meltano_resource, meltano_run_op

@job(resource_defs={"meltano": meltano_resource})
def run_elt_job():
    tap_done = meltano_run_op("tap-github target-bigquery")()

# Schedule to run daily at midnight
elt_schedule = ScheduleDefinition(
    job=run_elt_job,
    cron_schedule="0 0 * * *",
)

defs = Definitions(
    jobs=[run_elt_job],
    schedules=[elt_schedule],
)

📊 Dagster Configuration Example

from dagster import Definitions, ScheduleDefinition, job
from dagster_dbt import dbt_cli_resource, dbt_run_op, dbt_test_op

@job(resource_defs={"dbt": dbt_cli_resource})
def dbt_pipeline():
    dbt_run = dbt_run_op()
    dbt_test_op(start_after=dbt_run)

# Schedule to run daily
dbt_schedule = ScheduleDefinition(
    job=dbt_pipeline,
    cron_schedule="0 2 * * *",  # 2 AM daily
)

defs = Definitions(
    jobs=[dbt_pipeline],
    schedules=[dbt_schedule],
)

This sets up a complete DBT pipeline with automated testing that runs daily at 2 AM

🔄 Complete Data Testing Workflow

Integrate both Great Expectations and DBT into your data pipeline

In plain English

Neither tool replaces the other — they guard different stages of the same journey. Great Expectations stands at the door checking data as it arrives; DBT testing stands at the exit checking data after it's been reshaped. Using both means bad data gets caught wherever it shows up.

📋 Recommended Testing Strategy

Use Great Expectations for:

  • ✓ Raw data ingestion validation
  • ✓ File-based data sources
  • ✓ Complex statistical validations
  • ✓ Pre-transformation checks
  • ✓ Data quality monitoring

Use DBT Testing for:

  • ✓ Transformed data validation
  • ✓ Database table testing
  • ✓ Schema validation
  • ✓ Business logic verification
  • ✓ Integration testing

🎯 Example Pipeline

Stage 1: Ingestion

Tool: Great Expectations

Validate raw data from source systems

  • Check file formats
  • Verify column existence
  • Validate data types
→
Stage 2: Transformation

Tool: DBT

Transform and model data

  • Create dimensional models
  • Apply business logic
  • Generate aggregations
→
Stage 3: Validation

Tool: DBT Testing

Validate transformed data

  • Run schema tests
  • Verify relationships
  • Check business rules
